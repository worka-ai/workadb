# Worka Embedded Postgres (workadb) Specification
Status: Draft
Date: 2026-01-13

## Abstract
This document specifies Worka Embedded Postgres ("workadb"), a native,
in-process embedding of PostgreSQL 18.1 designed to run on iOS, Android,
and desktop targets without a server process. The purpose is to provide
full PostgreSQL SQL execution semantics with a small, stable host API and
predictable runtime behavior suitable for mobile constraints. The
specification defines the architecture, lifecycle, and the required host
APIs. It also describes non-goals, security considerations, and platform
constraints.

The intent is to avoid network servers, sockets, and external processes,
while preserving PostgreSQL's semantics and durability guarantees through
an embedded, single-process execution model.

## Status of This Memo
This document is an internal Worka RFC. It is written in the style of
IETF RFCs to be unambiguous and implementable by independent teams.

## Conventions and Normative Language
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119.

## 1. Motivation
Worka runs on mobile, desktop, and web. On mobile and desktop, the runtime
needs a local, durable, fully featured SQL engine with PostgreSQL
semantics. Running a PostgreSQL server process is unacceptable on mobile
due to process lifecycle restrictions, background execution limits, and
resource constraints. SQLite is insufficient for some of Worka's
requirements and would fragment behavior across platforms.

workadb provides a single embedded PostgreSQL backend, allowing:
- full PostgreSQL 18.1 SQL semantics on iOS/Android/desktop,
- no server process and no TCP listeners,
- controlled execution via a small host API,
- identical behavior across local and server deployments.

This replaces the "Postgres server in a box" model with a deterministic,
host-driven execution model that still executes the upstream PostgreSQL
code path for query planning, execution, and storage.

## 2. Goals
The system MUST:
- embed PostgreSQL 18.1 natively in-process,
- require no postmaster, no daemon, and no TCP sockets,
- allow the host to drive execution deterministically,
- preserve PostgreSQL SQL semantics and ACID guarantees,
- provide a stable, minimal host API that remains backward compatible,
- support iOS, Android, and desktop with the same behavior.

In addition, the system MUST embody the following principles:
- Zero-config operation: a caller SHOULD be able to use workadb with
  only a data path and no additional configuration files or flags.
- Single-path storage: the host supplies exactly one path to represent
  the database, and all internal storage details are hidden behind that
  path.

## 3. Non-Goals
The system is NOT required to:
- provide compatibility with PGlite or WASM environments,
- expose a network server or pgwire listener,
- support multi-process shared memory or background workers,
- provide general-purpose OS-level superuser access,
- replicate or replace the full PostgreSQL deployment toolchain.

## 4. Definitions
- Host: The application embedding workadb (Worka runtime, test harness,
  or any consumer).
- Engine: The embedded PostgreSQL backend instance.
- Handle: Opaque pointer/reference returned by the API identifying a
  single engine instance.
- Step: A single host-driven execution tick that processes one request
  and returns a response.
- Request: An execution unit provided by the host (SQL or protocol bytes).
- Response: The output generated by the engine after a Step.
- WEPG: The Worka Embedded Postgres C ABI prefix used for exported
  functions and types (e.g., `wepg_init`, `wepg_status`).

## 5. Architecture Overview
workadb embeds the PostgreSQL backend code into the host process and
provides a controlled entrypoint. It does not run a postmaster or listen
on sockets. Instead, the host provides requests to the engine and pulls
responses out.

At a high level:

```
Host Process
  +--------------------+
  | workadb API        |
  |  - init            |
  |  - step            |
  |  - shutdown        |
  +--------------------+
            |
            v
  +--------------------+
  | PostgreSQL Backend |
  |  - parser          |
  |  - planner         |
  |  - executor        |
  |  - storage engine  |
  +--------------------+
```

### 5.1 Embedded Single-User Backend
The embedded engine MUST use PostgreSQL's single-user backend execution
path. This avoids a postmaster, background workers, and multi-process
shared memory. The engine is therefore:
- in-process,
- single-threaded per handle,
- driven only by host-provided Steps.

### 5.2 In-Memory I/O Channel
All I/O to the backend MUST be via in-memory buffers supplied by the
host. No TCP or Unix sockets are used. The engine reads input bytes from
the buffer and writes response bytes into an output buffer.

The protocol encoding used for requests/responses is defined in Section 8.

## 6. Data Directory and initdb
PostgreSQL requires an initialized data directory (PGDATA). workadb MUST
provide an in-process initdb sequence.

### 6.1 Data Directory Rules
- The host MUST pass an absolute path for PGDATA.
- The engine MUST treat PGDATA as the sole source of persistent state.
- The engine MUST NOT write outside PGDATA and its configured temp paths.
- The host SHOULD ensure the path is in the app sandbox on mobile.

### 6.2 initdb Behavior
The engine MUST expose an initdb operation that:
- initializes PGDATA if it does not exist,
- is idempotent (safe to call on existing DB),
- does not fork external processes.

If initdb fails, the engine MUST return a structured error and leave
PGDATA in a consistent state.

### 6.3 Versioning
workadb MUST embed PostgreSQL 18.1. The engine MUST validate that the
existing PGDATA is compatible with the embedded major version and return
an error if not.

### 6.4 Single-Path Storage (Zero-Config)
To emulate SQLite-style deployment simplicity, workadb MUST treat the
database as a single host-visible path. The host MUST NOT be required to
manage or understand internal files. The engine MAY implement this as:
- a directory layout under the provided path, or
- a single-file container (e.g., a `.wpg` bundle) with an internal VFS.

If a single-file container format is not supported on a platform, the
engine MUST return `WEPG_ERR_UNSUPPORTED` with a clear error detail. The
default behavior SHOULD accept a directory path with no additional flags.

## 7. Process and Concurrency Model
Each engine handle is a single-user backend instance. The host MUST
serialize calls per handle. The engine MUST NOT be called concurrently on
the same handle.

The host MAY create multiple handles to achieve parallelism, but should
assume:
- increased memory usage,
- separate transaction states,
- no automatic cross-handle coordination.

## 8. Request/Response Protocol
workadb supports two request modes:
1) SQL Mode (required)
2) Wire Mode (optional)

### 8.1 SQL Mode (Required)
SQL Mode provides a simple API that accepts a UTF-8 SQL string and
returns structured results. It does NOT require the PostgreSQL wire
protocol.

In SQL Mode, the engine MUST:
- parse and execute the SQL using PostgreSQL internals,
- honor PostgreSQL semantics (transaction control, types, NULL behavior),
- return row data and column metadata in a deterministic format.

### 8.2 Wire Mode (Optional)
Wire Mode accepts PostgreSQL protocol frames and returns protocol frames.
This mode is OPTIONAL. If implemented, it MUST conform to PostgreSQL 18.1
frontend/backend protocol semantics for the supported message subset.

Wire Mode MUST NOT require a network socket; it runs over in-memory
buffers only.

#### 8.2.1 Wire Mode Framing
The request buffer MAY contain a single protocol message or multiple
messages back-to-back. The engine MUST parse messages according to the
PostgreSQL v3 frontend/backend protocol.

A single `wepg_step` call in Wire Mode MUST:
- consume at least one complete frontend message if one is available,
- produce all corresponding backend messages required for that input,
- return after reaching a protocol boundary (typically `ReadyForQuery`)
  or when input is exhausted.

If the input buffer ends in a partial message, the engine MUST return
`WEPG_ERR_EXEC_FAILED` with an error detail indicating incomplete input.

#### 8.2.2 Supported Message Subset
Wire Mode implementations MUST support, at minimum:
- StartupMessage
- Query (`Q`)
- Parse (`P`)
- Bind (`B`)
- Execute (`E`)
- Sync (`S`)
- Close (`C`)
- Terminate (`X`)

The engine MUST emit standard backend messages including:
- AuthenticationOk
- ParameterStatus
- BackendKeyData (optional, may be zeroed)
- ReadyForQuery
- RowDescription
- DataRow
- CommandComplete
- ErrorResponse
- NoticeResponse

If a client sends an unsupported message type, the engine MUST return an
ErrorResponse and leave the connection in a consistent state.

### 8.3 SQL Mode Response Encoding (Required)
SQL Mode responses use a Worka-specific binary frame that is stable
across bindings. The response format is intentionally simple and is not
the PostgreSQL wire protocol.

The response frame is:

```
u32  version          // MUST be 1
u32  column_count
u32  row_count         // 0 if no rows; MAY be 0 for unknown
repeat column_count:
  u32 name_len
  bytes name           // UTF-8 column name
  u32 type_oid         // PostgreSQL type OID
  i16 type_len         // -1 if variable length
  i32 type_mod         // -1 if not applicable
repeat row_count:
  repeat column_count:
    i32 value_len      // -1 for NULL
    bytes value        // raw bytes in PostgreSQL text format
```

If the engine cannot determine `row_count` in advance, it MUST set
`row_count` to 0 and still emit rows. In that case, the host MUST parse
until the end of the response buffer.

## 9. Host API (Normative)
The host API is defined as a C ABI. Other language bindings MUST map
directly to this ABI without changing semantics.

### 9.0 Configuration
```
typedef struct {
  const char* pgdata_path;     // REQUIRED, absolute path
  const char* temp_path;       // OPTIONAL, defaults to pgdata_path
  uint32_t flags;              // bitmask, see WEPG_FLAG_*
  uint32_t max_response_bytes; // OPTIONAL, 0 means no limit
} wepg_config;

enum {
  WEPG_FLAG_ENABLE_WIRE = 1 << 0,
  WEPG_FLAG_READONLY = 1 << 1,
  WEPG_FLAG_DISABLE_DYNAMIC_EXT = 1 << 2,
  WEPG_FLAG_NO_AUTO_INITDB = 1 << 3
};
```

`pgdata_path` MUST be provided. `temp_path` MAY be NULL. If
`max_response_bytes` is non-zero, the engine MUST cap response output to
that size and return `WEPG_ERR_BUFFER_TOO_SMALL` when exceeded.

Unless `WEPG_FLAG_NO_AUTO_INITDB` is set, the engine SHOULD initialize
PGDATA automatically when it does not exist. This enables zero-config
use with only a path.

### 9.1 Initialization
```
wepg_status wepg_init(const wepg_config* config, wepg_handle* out);
```
Behavior:
- Initializes the engine.
- Validates paths and configuration.
- Returns a handle on success.

### 9.2 initdb
```
wepg_status wepg_initdb(wepg_handle handle);
```
Behavior:
- Creates PGDATA if missing.
- Safe to call multiple times.

### 9.3 Asset Extraction (Normative)
```
wepg_status workadb_assets_install(const char* dir_path);
```
Behavior:
- Extracts embedded WorkaDB assets into `dir_path`.
- MUST be idempotent if the assets already exist.
- MUST return `WEPG_ERR_INVALID_CONFIG` when `dir_path` is NULL/empty.
- MUST return `WEPG_ERR_INTERNAL` on extraction failures.

The extraction MUST produce the following layout:
```
<dir_path>/
  bin/postgres
  share/postgresql/...
  share/workadb/pgdata-template/...
```

If the host uses `workadb_assets_install`, it SHOULD set:
- `WORKADB_EXEC_PATH=<dir_path>/bin/postgres`
- `WORKADB_TEMPLATE_PATH=<dir_path>/share/workadb/pgdata-template`

This enables zero-config `wepg_initdb` without requiring the caller to
ship or manage the template files separately.

### 9.4 Step Execution
```
wepg_status wepg_step(
    wepg_handle handle,
    const wepg_request* request,
    wepg_response* response
);
```
Behavior:
- Executes exactly one request.
- Writes response into a host-managed buffer (see 9.6).
- MUST NOT block waiting for external input.

### 9.5 Reset
```
wepg_status wepg_reset(wepg_handle handle);
```
Behavior:
- Resets session state (prepared statements, portals, temp tables).
- Does NOT destroy PGDATA.

### 9.6 Shutdown
```
wepg_status wepg_shutdown(wepg_handle handle);
```
Behavior:
- Flushes WAL and checkpoints as needed.
- Releases engine resources.
- Invalidates the handle.

### 9.7 Buffer Ownership
The host controls all buffer allocations.
- Requests supply input buffers.
- Responses are written into host-provided buffers.
- If a response exceeds capacity, the engine MUST return
  `WEPG_ERR_BUFFER_TOO_SMALL` and report the required size.

### 9.8 ABI Versioning
```
uint32_t wepg_abi_version(void);
const char* wepg_version_string(void);
```

`wepg_abi_version` returns a 32-bit version where the high 16 bits are
the ABI major version and the low 16 bits are the ABI minor version.
ABI major MUST increment on any breaking change. ABI minor MUST only
increment on additive changes.

`wepg_version_string` MUST return a human-readable version string that
includes the embedded PostgreSQL version and the workadb build version.

## 10. Request/Response Structures
The structures below are normative. Fields marked OPTIONAL MAY be NULL.

```
typedef enum {
  WEPG_MODE_SQL = 1,
  WEPG_MODE_WIRE = 2
} wepg_mode;

typedef struct {
  wepg_mode mode;
  const uint8_t* bytes;
  size_t len;
} wepg_request;

typedef struct {
  uint8_t* bytes;
  size_t len;          // actual bytes written
  size_t capacity;     // buffer capacity
  int64_t rows;        // row count if known
} wepg_response;
```

## 11. Error Model
All API calls return `wepg_status`.

```
typedef enum {
  WEPG_OK = 0,
  WEPG_ERR_INVALID_CONFIG,
  WEPG_ERR_INITDB_FAILED,
  WEPG_ERR_EXEC_FAILED,
  WEPG_ERR_BUFFER_TOO_SMALL,
  WEPG_ERR_INCOMPATIBLE_PGDATA,
  WEPG_ERR_UPGRADE_REQUIRED,
  WEPG_ERR_UNSUPPORTED,
  WEPG_ERR_INTERNAL
} wepg_status;
```

The engine MUST expose an error detail API:
```
const char* wepg_last_error(wepg_handle handle);
```

## 12. Logging and Diagnostics
workadb MUST provide a pluggable logger:
```
typedef void (*wepg_log_fn)(int level, const char* msg, void* ctx);
void wepg_set_logger(wepg_log_fn fn, void* ctx);
```

The engine MUST emit:
- initdb progress and failures,
- query errors,
- fatal errors/panics,
- WAL/checkpoint warnings.

## 13. Extensions
Extensions MAY be built in statically. Dynamic extension loading SHOULD
be disabled by default on mobile.

The engine MUST provide a safe allowlist for extensions if dynamic load
is enabled.

## 14. Security Considerations
- The host MUST treat SQL input as untrusted and enforce authorization
  above the engine.
- The engine MUST NOT open network sockets.
- The engine MUST restrict file access to PGDATA and configured temp
  directories.
- The host SHOULD rely on OS-level sandboxing for filesystem isolation.

## 15. Portability Considerations
workadb MUST support:
- iOS (arm64, simulator and device),
- Android (arm64, x86_64 as needed),
- Desktop (macOS, Linux, Windows).

Platform-specific changes MUST be isolated to a portability layer. The
PostgreSQL core code SHOULD remain as close to upstream as possible.

### 15.1 Portability Layer Boundaries
To keep merges with upstream PostgreSQL safe and predictable, the
embedded implementation MUST obey these boundaries:

Allowed changes:
- New `src/embed/*` layer for the public C API, buffer plumbing, and
  host-driven loop.
- `src/backend/libpq/*` for in-memory I/O shims (no sockets).
- `src/backend/postmaster/*` to disable postmaster entrypoints.
- `src/backend/storage/ipc/*` to avoid shared memory or background
  workers in single-user mode.
- `src/port/*` for platform-specific adaptations (signals, clocks,
  file paths).

Prohibited changes (unless explicitly approved by a separate RFC):
- Parser, planner, optimizer, executor.
- Storage engine semantics (WAL, MVCC, visibility rules).
- System catalog layout and behavior.

These boundaries ensure that PostgreSQL semantics remain unchanged and
that workadb can track upstream releases with a bounded patch surface.

### 15.2 Embedded Build Profile (Non-Normative)
WorkaDB defines an "embedded profile" build intended to reduce binary
size while preserving PostgreSQL SQL semantics. The recommended configure
flags are:

```
--without-llvm
--with-openssl=no
--without-gssapi
--without-ldap
--without-pam
--without-readline
--without-lz4
--without-zstd
--without-bonjour
--without-systemd
--without-selinux
--disable-nls
```

Notes:
- ICU SHOULD be kept enabled when available to preserve Unicode collation
  behavior across locales. The profile therefore omits `--without-icu`.
- The embedded build SHOULD include only `plpgsql` from core languages.
- Contrib and FDW extensions SHOULD be omitted unless explicitly required.
  If an FDW is shipped, only `postgres_fdw` is recommended.

## 16. Compatibility and Upgrades
The engine MUST embed a single major version (18.1). Upgrades across
major versions require explicit migration steps defined by Worka. Minor
version updates SHOULD be drop-in compatible.

### 16.1 Incompatible Data Handling
If the on-disk data directory is incompatible with the embedded major
version, `wepg_init` MUST fail with `WEPG_ERR_UPGRADE_REQUIRED`. The
error detail MUST include the detected on-disk major version.

### 16.2 Migration Procedure (Normative)
When an upgrade is required, the host MUST:
1) Create a new PGDATA directory for the target version.
2) Export all user data from the old PGDATA using a logical dump.
3) Import the dump into the new PGDATA.
4) Atomically replace the old PGDATA with the new PGDATA.

The engine MUST provide at least one of the following mechanisms:
- an embedded logical dump API, or
- a documented, host-driven SQL export/import path.

On mobile platforms, the preferred method is an in-process logical
dump/restore to avoid external tooling.

### 16.3 ABI Compatibility
Within a given ABI major version, all functions defined in this
specification MUST remain binary compatible. Fields may be added only at
the end of structs, and only when gated by an ABI minor version bump.

## 17. Rust FFI Bindings
Rust bindings MUST map directly to the C ABI using `#[repr(C)]` structs
and `extern "C"` declarations. Handles are opaque and MUST be treated as
non-thread-safe unless explicitly synchronized by the host.

### 17.1 Rust Type Mapping
```
#[repr(C)]
pub struct WepgConfig {
    pub pgdata_path: *const ::std::os::raw::c_char,
    pub temp_path: *const ::std::os::raw::c_char,
    pub flags: u32,
    pub max_response_bytes: u32,
}

#[repr(C)]
pub struct WepgRequest {
    pub mode: u32,
    pub bytes: *const u8,
    pub len: usize,
}

#[repr(C)]
pub struct WepgResponse {
    pub bytes: *mut u8,
    pub len: usize,
    pub capacity: usize,
    pub rows: i64,
}

extern "C" {
    fn wepg_init(cfg: *const WepgConfig, out: *mut *mut ::std::os::raw::c_void) -> i32;
    fn wepg_initdb(handle: *mut ::std::os::raw::c_void) -> i32;
    fn wepg_step(handle: *mut ::std::os::raw::c_void, req: *const WepgRequest, resp: *mut WepgResponse) -> i32;
    fn wepg_reset(handle: *mut ::std::os::raw::c_void) -> i32;
    fn wepg_shutdown(handle: *mut ::std::os::raw::c_void) -> i32;
    fn wepg_last_error(handle: *mut ::std::os::raw::c_void) -> *const ::std::os::raw::c_char;
}
```

### 17.2 Safety Rules
- The handle MUST be wrapped in a Rust type that enforces exclusive
  access (e.g., `Mutex` or single-threaded use).
- All pointers passed to C MUST remain valid for the duration of the
  call.
- Response buffers MUST be allocated by Rust and passed by pointer; C
  MUST NOT free them.
- The Rust wrapper SHOULD translate `wepg_status` into a Rust `Result`
  with a structured error type.

## 18. Other Language Embeddings
Bindings for other languages MUST remain thin and MUST preserve the C ABI
semantics. All language bindings MUST:
- pass raw buffers without copying where possible,
- uphold buffer ownership rules (Section 9.6),
- serialize access to a handle unless explicitly synchronized.

### 18.1 Node.js (N-API)
Node.js bindings SHOULD use N-API to avoid ABI churn across Node
versions. The binding SHOULD expose:
- `init(config) -> handle`
- `initdb(handle)`
- `step(handle, request, responseBuffer) -> response`
- `reset(handle)`
- `shutdown(handle)`
- `lastError(handle)`

The binding MUST:
- require callers to pass a `Buffer` for response output,
- return the actual byte length and row count,
- surface `wepg_status` as a typed JS error with `code` and `message`.

### 18.2 Python (CPython C-API)
Python bindings SHOULD use the CPython C-API rather than ctypes for
performance and predictable memory ownership.

The binding MUST:
- expose a `WorkaDb` class holding the native handle,
- accept and return `bytes` or `bytearray` for request/response,
- ensure the GIL is released during `wepg_step` if it may block.

The binding SHOULD provide context manager support:
```
with WorkaDb(config) as db:
    db.initdb()
    resp = db.step_sql("SELECT 1")
```

### 18.3 Java (JNI)
Java bindings SHOULD use JNI. The binding MUST:
- use a long to hold the native handle pointer,
- enforce handle validity checks on every call,
- use direct `ByteBuffer` for response buffers to avoid copies.

The binding SHOULD expose:
- `init(Config) -> long`
- `initdb(long)`
- `step(long, ByteBuffer req, ByteBuffer resp) -> ResponseMeta`
- `reset(long)`
- `shutdown(long)`

### 18.4 Common Binding Requirements
All bindings MUST:
- propagate `wepg_last_error` details on non-OK status,
- provide deterministic shutdown (finalizer is not sufficient),
- document thread-safety and reentrancy explicitly.

## 19. Rationale for Design
The single-step, host-driven model:
- avoids background process management on mobile,
- makes scheduling deterministic and testable,
- isolates engine crashes from host control flow,
- preserves full PostgreSQL semantics without a network server.

This mirrors the successful pattern used by PGlite but is native and free
of WASM constraints.
